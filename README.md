# my-service-agent: 반품·교환 정책 안내 챗봇 설계

## 서비스 소개

온라인 쇼핑몰 고객이 "이거 반품돼?", "교환 배송비 누가 내?"처럼 물으면, 정책 문서의 조항을 근거로 답하는 안내 챗봇이다. 고객의 주문이 반품 가능한지 판정하고, 고객이 확인하면 반품을 접수한다. 정책 예외나 판단이 애매한 경우는 담당자에게 넘긴다.

이 저장소는 구현이 아니라 **설계 문서**이다. 도구 계약, 권한, 실패 뒤 행동, 테스트, 트레이스 양식을 정리했다.

| 파일 | 내용 |
|---|---|
| `design-packet.md` | 설계 패킷 7항목 (시스템 지시, 도구 계약 4개, 권한, 오류·이관, 반환 규약, 테스트 8개, 트레이스 양식) |
| `my-agent/tool-definition.md` | 실습 1: 재고 조회 도구 정의서와 실패 사례 분석 |
| `my-agent/inventory_tool.py`, `inventory_tool_v2.py` | 실습 2: 재고 도구 실행 코드 (v2는 도구 설명 한 곳만 수정) |
| `my-agent/traces/` | 실습 2 실행 기록 원문 (trace-01~04, trace-mcp-01) |

## 설계 결정 요약

### 도구를 네 개만 둔 이유
고객 문의는 "정책이 뭐야 / 내 주문이 어때 / 내 주문은 반품돼 / 반품해 줘" 네 가지로 나뉘어서, 질문 유형 하나에 도구 하나가 대응하도록 했다. 정책 검색과 가능 여부 판정을 한 도구로 합치면 모델이 일반 질문에도 주문번호를 요구하거나, 반대로 주문 판정을 정책 검색만으로 추측할 수 있어서 나눴다. 환불 금액 계산이나 배송 조회는 이 챗봇의 범위가 아니므로 도구로 만들지 않았다.

### 권한을 나눈 기준
상태를 바꾸는지가 기준이다. 읽기 도구 세 개는 챗봇이 바로 쓰고, 쓰기 도구인 반품 접수는 고객 확인(`customer_confirmed`)과 직전 판정 결과를 하네스가 대조한 뒤에만 실행한다. 정책 예외 승인, 개인정보 열람, 환불 확정은 되돌리기 어렵거나 사람의 판단이 필요해서 아예 도구로 주지 않고 이관으로만 처리한다.

### 실패 뒤 행동을 그렇게 정한 근거
실습 2에서 2B 모델이 "부산 3번 창고"를 허용 코드 `BUSAN-02`로 바꿔 넣고 수량을 확정해 답하는 것을 봤다(trace-02). 도구 설명만 고쳐서는 막지 못했다(trace-03). 그래서 정보가 모자라면 "추측 대신 질문"을 기본으로 하고, 같은 오류가 두 번이면 루프를 멈추고 이관하도록 했다. 쓰기 도구의 `TIMEOUT`은 접수가 됐는지 알 수 없어 재시도하면 중복 접수가 생길 수 있으므로, 재시도하지 않고 이관한다.

## 실습에서 관찰한 것 (설계의 근거)

| 트레이스 | 관찰 | 설계에 반영한 점 |
|---|---|---|
| trace-01 | 정상 요청: 요청 → 실행 → 결과를 근거로 답, 모두 통과 | [1] 모델 요청 / [2] 하네스 실행 / [3] 답을 나눠 기록하는 트레이스 양식 |
| trace-02 | "부산 3번 창고" → 모델이 `BUSAN-02`로 추측해 넣음. 하네스 허용 목록 검사도 통과 | 스키마 검사만으로는 "있는 값으로 바꿔 넣는" 추측을 못 막는다 → 누락 정보는 질문으로 |
| trace-03 | 도구 설명 한 곳만 고쳤지만 3회 모두 같은 추측 | 설명(프롬프트)만 믿지 않고 하네스 검사(확인 플래그, 직전 판정 대조)를 둠 |
| trace-04 | 없는 코드(`DAEGU-01`)는 `WAREHOUSE_NOT_ALLOWED`로 막히고, 모델은 수량을 지어내지 않고 다시 물음 | 오류 코드를 명확히 돌려주면 실패 뒤 행동이 잘 작동한다 → 오류 코드별 행동표 |
| trace-mcp-01 | Qdrant MCP 연결 시 store/find 두 도구가 주입되어 각각 맞게 선택됨. 연결 실패 시에는 도구가 없어 작업을 멈춤 | 정책 검색 도구(search_return_policy)를 RAG MCP로 붙이는 구조 |

## 실행하지 않은 것과 이유

- **챗봇 구현:** 과제 범위가 설계 문서이므로 네 도구와 하네스는 구현하지 않았다.
- **opencode 비교 실험:** 이 PC에 opencode CLI가 설치되어 있지 않아 Claude Code로만 실행했다. 같은 `opencode.json`으로 실행해 trace-mcp-02로 남길 예정이다.
- **하네스 쪽 방어 실험:** trace-03에서 도구 설명 수정이 효과가 없었다. 다음 한 곳 수정으로 "사용자 원문에 창고 코드가 그대로 없으면 실행 전에 되묻는 하네스 검사"를 시험하지 못했다.
- **정책 문서 RAG:** 실제 반품 정책 문서를 Qdrant에 넣고 T1, T4, T7을 돌려 보지 않았다. 임베딩 모델이 영어용(`bge-small-en-v1.5`)이라 한국어 정책 검색 정확도도 따로 확인해야 한다.

### 다음에 측정할 지점
1. 테스트 T1~T8을 실제로 실행했을 때 기대 도구·기대 행동과 일치하는 비율
2. T5, T8(승인 우회 요청)에서 `create_return_request`가 한 번이라도 호출되는지 (0회가 목표)
3. 다국어 임베딩 모델로 바꿨을 때 정책 검색 1위 정답률 변화
4. 도구 설명, 스키마, 하네스 검사를 **한 번에 하나씩** 바꾸며 trace-02 유형 추측이 사라지는 지점

## 실습 환경

- macOS, Python 3.14 (MCP 서버는 Python 3.12로 실행), uv 0.13.0, Ollama 0.40.0, qwen3.5:2b
- 교재와 다른 점
  - Ollama 0.40.0은 모델을 GGUF 한 파일이 아닌 텐서 조각으로 저장해서, 채팅 템플릿을 `tokenizer_config.json`에서 읽었다.
  - Python 3.14에서 `mcp-server-qdrant` 의존성 빌드가 실패해, `uvx --python 3.12`로 실행했다.
