# my-service-agent: 음향 프로그램 단축키 검색 챗봇 설계

## 서비스 소개

음향 프로그램(DAW)을 쓰다가 "이 작업 단축키가 뭐였지?" 할 때 묻는 챗봇이다. 프로그램 이름과 하고 싶은 작업을 말하면 공식 단축키 문서를 근거로 단축키를 찾아 준다.

- 예: "Pro Tools에서 재생을 멈추는 단축키가 뭐야?", "클립을 분리하는 단축키를 알려 줘."
- 지원 프로그램: Pro Tools, Logic Pro, Ableton Live, REAPER (기본 단축키만)
- 핵심 요구: **정확한 단축키**를 찾고, **운영체제(macOS / Windows)와 버전에 따라 다르면 구분**해서 알려 준다.

이 저장소는 구현이 아니라 **설계 문서**이다.

| 파일 | 내용 |
|---|---|
| `design-packet.md` | 설계 패킷 7항목 (시스템 지시, 도구 계약 3개, 권한, 오류·이관, 반환 규약, 테스트 8개, 트레이스 양식) |
| `my-agent/tool-definition.md` | 실습 1: 재고 조회 도구 정의서와 실패 사례 분석 |

| `my-agent/traces/` | 실습 2 실행 기록 원문 (my-trace-01~04, my-trace-mcp-01: 직접 실행 / trace-01~04, trace-mcp-01: 사전 실행) |

## 설계 결정 요약

### 도구를 세 개만 둔 이유
사용자 질문은 "어떤 프로그램인지 확정 → 그 프로그램에서 단축키 찾기" 두 단계로 나뉘고, 여기에 "틀린 단축키 제보" 하나가 더해진다. 프로그램 확정(resolve_program)을 검색에서 떼어 낸 이유는 "프툴", "로직" 같은 별칭과 지원하지 않는 프로그램을 검색 전에 걸러야, 모델이 프로그램을 추측한 채 단축키를 찾는 일이 없기 때문이다. OS별·버전별 비교를 따로 도구로 만들지 않고 search_shortcut의 반환 형식(OS를 키로, 적용 버전 포함)에 넣어, 도구끼리 "쓰는 때"가 겹치지 않게 했다.

### 권한을 나눈 기준
상태를 바꾸는지가 기준이다. 단축키 검색 두 개는 읽기라서 챗봇이 바로 쓰지만, 오류 제보는 관리자 대기열에 기록이 남는 쓰기라서 사용자 확인 뒤에만 접수한다. 단축키 DB 수정은 잘못 고치면 모든 사용자에게 틀린 답이 나가므로 챗봇에게 주지 않고, 관리자가 공식 문서와 대조해서만 고치게 했다.

### 실패 뒤 행동을 그렇게 정한 근거
실습 2에서 2B 모델이 "부산 3번 창고"를 허용 코드 `BUSAN-02`로 바꿔 넣고 수량을 확정했고, 도구 설명을 고쳐도 그대로였다(my-trace-03, 04). 단축키에서도 같은 일이 생길 수 있다. OS를 말하지 않으면 모델이 macOS로 추측하거나, 없는 버전을 가까운 버전으로 바꿔 넣을 수 있다. 그래서 `os`에 `UNKNOWN` 값을 두어 추측 대신 두 OS를 모두 보여 주게 했고, 없는 버전은 `VERSION_NOT_COVERED`로 돌려준 뒤 반드시 묻게 했다. 지원하지 않는 프로그램은 모델이 "아마 이 단축키일 것"이라고 지어내기 쉬우므로, 재시도 없이 바로 중단한다.

## 실습에서 관찰한 것 (설계의 근거)

| 트레이스 | 관찰 | 설계에 반영한 점 |
|---|---|---|
| my-trace-01 | 정상 요청: 모델은 요청만, 하네스가 실행, 모델이 결과를 그대로 옮겨 답함 | 단축키는 반드시 search_shortcut 반환값만 답에 쓴다 (⑤-7) |
| my-trace-02 | "부산 2번" → 확인 없이 `BUSAN-02`로 번역 | 별칭("프툴")은 모델이 바꾸지 않고 resolve_program이 확정한다 |
| my-trace-03 | "부산 3번" → 숫자를 무시하고 `BUSAN-02`로 추측. 허용값이라 하네스도 통과 | `os`, `version`은 사용자가 말한 값만 넣고, 모르면 `UNKNOWN` / 비움 |
| my-trace-04 | 도구 설명 한 곳만 고쳐도 호출은 그대로 | 설명(프롬프트)만 믿지 않고, 쓰기 도구는 하네스가 직전 호출 기록을 대조 |
| my-trace-mcp-01 | Qdrant MCP를 설정 파일로 붙이자 store/find가 주입되어 맞게 선택됨. 뜻이 비슷한 문장을 1위로 찾음 | search_shortcut은 공식 단축키 문서를 Qdrant 같은 RAG MCP로 붙여 구현할 수 있다 |

## 실행하지 않은 것과 이유

- **챗봇 구현:** 과제 범위가 설계 문서이므로 세 도구와 하네스는 구현하지 않았다.
- **단축키 DB 구축:** 네 프로그램의 공식 단축키 문서를 OS·버전별로 정리해 Qdrant에 넣는 일은 하지 않았다. 문서마다 표기 방식이 달라(⌘ / Cmd / Command) 정규화 규칙을 먼저 정해야 한다.
- **opencode 비교 실험:** 실습 2의 opencode 실험은 건너뛰고 Claude Code로만 실행했다.
- **임베딩 모델 검증:** 실습의 `bge-small-en-v1.5`는 영어용이다. "클립 분리" 같은 한국어 질문과 영어 공식 기능 이름("Split Clip")을 잘 잇는지 확인하지 않았다.

### 다음에 측정할 지점
1. T1~T8을 실제로 실행했을 때 기대 도구·기대 행동과 일치하는 비율
2. **OS 구분:** OS를 말하지 않은 질문(T3)에서 모델이 `os=UNKNOWN`을 넣는 비율, 하나의 OS로 추측하는 비율
3. **버전 구분:** DB에 없는 버전(T4)에서 다른 버전 값을 그 버전의 답처럼 말하는지
4. **정확도:** 최종 답의 단축키가 search_shortcut 반환값과 글자까지 같은 비율 (모델이 단축키를 바꿔 말하지 않는지)
5. T7, T8에서 `report_shortcut_issue`가 확인 없이 호출되는 횟수 (0회가 목표)

## 실습 환경

- macOS, Python 3.14 (MCP 서버는 Python 3.12로 실행), uv 0.13.0, Ollama 0.40.0, qwen3.5:2b
- 교재와 다른 점
  - Ollama 0.40.0은 모델을 GGUF 한 파일이 아닌 텐서 조각으로 저장해서, 채팅 템플릿을 `tokenizer_config.json`에서 읽었다.
  - Python 3.14에서 `mcp-server-qdrant` 의존성 빌드가 실패해, `uvx --python 3.12`로 실행했다.
